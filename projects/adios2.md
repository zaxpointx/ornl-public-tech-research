## Walkthrough (plain language)
- **What it is:** a C++ library, with Python, C, Fortran and MATLAB bindings, that a simulation calls to save or send its data. It sends named arrays to a file, over a network, or straight into another program's memory, all through one API. [KNOWN: [ReadMe.md L13-L30](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/ReadMe.md#L13-L30)]
- **The problem:** supercomputers compute much faster than their file systems can store data (the "IO wall"). Workflows that park every intermediate result on disk slow down. ADIOS2's answer is to let the same code write to fast file formats or stream to a consumer, picked at run time. [KNOWN: OSTI 3002190 abstract, https://www.osti.gov/biblio/3002190; [nutshell.rst L41-L64](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/docs/user_guide/source/introduction/nutshell.rst#L41-L64)]
- **What goes in:** the application declares *variables* (named, typed, n-dimensional arrays, plus each process's piece of the global array), *attributes* (metadata), and *steps* (one group of variables per output time). [KNOWN: [components/overview.rst L11-L60](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/docs/user_guide/source/components/overview.rst#L11-L60)]
- **What happens:** an *engine*, chosen by name in code or in an XML/YAML config file, decides what a step turns into: BP5 files on disk, an SST network stream, an HDF5 file, DAOS objects, an in-memory handoff, and so on. *Operators* can compress each block on the way out (ZFP, SZ3, MGARD, Blosc2 and others). [KNOWN: [IO.cpp L72-L158](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/IO.cpp#L72-L158); [OperatorFactory.cpp L113-L220](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/operator/OperatorFactory.cpp#L113-L220)]
- **What comes out:** a self-describing dataset (BP files hold their own metadata) or a live stream a reader consumes step by step. Readers can ask for just a sub-box or a range of steps. [KNOWN: [VariableBase.h L177-L191](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/VariableBase.h#L177-L191)]
- **Where humans act:** a developer adds ADIOS2 calls to the code once. A user then picks the engine, transport, compression and aggregation in a config file, without recompiling. [KNOWN: archived CSMD page; [ADIOS.h L46-L60](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/ADIOS.h#L46-L60)]
- **What it is not:** the docs say it is not a file-only library, not MPI-only, not a hierarchical data model like HDF5 groups, and not a memory manager. [KNOWN: [nutshell.rst L56-L64](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/docs/user_guide/source/introduction/nutshell.rst#L56-L64)] It is also not a durable message queue: earlier portfolio work showed SST can drop steps when no readers are attached (docs/portfolio-expansion-2026-11-10/computing-instruments.md section 1). [KNOWN, from that packet]
- **Example:** the README's Python snippet writes a five-element array to `data.bp` with `adios2.Stream(..., "w")`, then loops over `f.steps()` to read it back. Changing the engine to SST in a config file would turn that same writer into a live stream to a separate analysis program. [KNOWN: [ReadMe.md L34-L50](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/ReadMe.md#L35-L53); INFERRED: the SST swap follows the runtime-engine design and SST paper, not tested here]
- **What's unknown:** current named production users per facility, download counts, and the DOE CODE record (none found).

## What it is (plain English, 2-4 sentences)
ADIOS2 is an I/O framework for scientific codes. It lets an application describe *what* data it produces (variables, attributes, steps) and leaves *how* it travels (file, network, memory, compression) to swappable engines and operators. [KNOWN: archived CSMD page; README] The project describes itself as "used in production on the world's largest supercomputers" and validated on Frontier, Summit and Perlmutter. That's the project's own claim, quoted from the README. [KNOWN: [ReadMe.md L14](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/ReadMe.md#L14), [L29](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/ReadMe.md#L29)]

## How it works (plain English, no jargon without definition)
1. **Set up.** The app creates one `ADIOS` object, scoped to an MPI communicator (the group of cooperating processes) and optionally given an XML config file. `ADIOS` is a factory for named `IO` objects. [KNOWN: [ADIOS.h L46-L89](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/ADIOS.h#L46-L89); overview.rst]
2. **Declare.** Each `IO` holds the variable and attribute definitions plus the engine choice. A variable has a global `Shape`, and each process gives its own `Start` and `Count`, the offset and size of its block. The shape kinds are GlobalValue, GlobalArray, JoinedArray, LocalValue and LocalArray. [KNOWN: [VariableBase.h L64-L66](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/VariableBase.h#L64-L66); [ADIOSTypes.h L50-L58](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/common/ADIOSTypes.h#L50-L58)]
3. **Open picks the engine.** `IO::Open` lowercases the engine name and looks it up in a factory table (bp3, bp4, bp5, sst, daos, hdf5, inline, null, plugin, campaign, timeseries and others). Engines not compiled in map to a placeholder that throws a clear error. If no engine is set, reads detect the format on disk, with rank 0 checking and broadcasting the answer to the other ranks, and writes default to BP5. [KNOWN: [IO.cpp L72-L158](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/IO.cpp#L72-L158), [L608-L726](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/IO.cpp#L608-L726)] New engines can be registered at run time through `IO::RegisterEngine`. [KNOWN: [IO.cpp L203-L207](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/IO.cpp#L203-L207)]
4. **Steps.** Writers and readers wrap work in `BeginStep()` / `EndStep()`. Readers get a status back: OK, NotReady, EndOfStream or OtherError. That is what lets the same loop read either a finished file or a stream that's still being written. [KNOWN: [Engine.h L105-L114](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/Engine.h#L105-L114), [L405-L413](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/Engine.h#L405-L413); [ADIOSTypes.h L101-L114](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/common/ADIOSTypes.h#L101-L114)] The docs say steps exist "to resemble actual production of data" in groups of variables. [KNOWN: [nutshell.rst L49](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/docs/user_guide/source/introduction/nutshell.rst#L49)]
5. **Put and Get are deferred by default.** `Put` registers data but may not copy it until `EndStep`, `PerformPuts` or `Close`, so the app mustn't reuse the buffer before then. `Mode::Sync` copies at once. Each engine implements the hooks `DoPutSync`/`DoPutDeferred` and `DoGetSync`/`DoGetDeferred`. [KNOWN: [Engine.h L140-L162](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/Engine.h#L140-L162), [L599-L636](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/Engine.h#L599-L636)] The stated reason: ADIOS2 "favors codes transferring a group of variables asynchronously". [KNOWN: [nutshell.rst L47](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/docs/user_guide/source/introduction/nutshell.rst#L47)]
6. **Operators transform blocks.** An operator implements `Operate` (forward, for example compress) and `InverseOperate`, and declares which data types it accepts. It is attached per variable with `AddOperation`. [KNOWN: [Operator.h L80-L93](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/Operator.h#L80-L93); [VariableBase.h L224-L226](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/VariableBase.h#L224-L226)]
7. **BP5 file engine.** It writes a directory of `data.N`, `md.0`, `md.idx` and `mmd.0` files and has been the default since 2.9. It aggregates through a fixed shared-memory segment per node instead of MPI sends. The docs say memory use can approach half of BP4's and metadata handling is faster with many variables. [KNOWN: [bp5.rst L5-L44](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/docs/user_guide/source/engines/bp5.rst#L5-L44); default aggregation TwoLevelShm at [BP5Engine.h L125-L130, L158](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/engine/bp5/BP5Engine.h#L125-L158)]
8. **SST streaming engine.** It is split into a *control plane* (`toolkit/sst/cp/`: who is connected, step metadata, queue policy) and pluggable *data planes* (`toolkit/sst/dp/`: evpath/TCP, rdma via libfabric, ucx, mercury, mpi, daos). `SelectDP` builds the list of compiled-in data planes and picks by priority or by the user's `DataTransport` choice. An environment variable can force one. [KNOWN: [dp.c L74-L106](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/toolkit/sst/dp/dp.c#L74-L106); the data-plane contract is a struct of function pointers, [dp_interface.h L327-L350](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/toolkit/sst/dp_interface.h#L327-L350)] Queue and drop semantics are in the earlier portfolio packet and aren't repeated here.
9. **Plugins.** The `plugin` engine loads a shared library named by the `PluginName`/`PluginLibrary` parameters, searched via `ADIOS2_PLUGIN_PATH`. Since 2.12 plugin engines implement a standalone `PluginEngineInterface` that uses only the public C++ API (interface v2). [KNOWN: [PluginEngine.cpp L42-L61](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/engine/plugin/PluginEngine.cpp#L42-L61); [adiosPluginManager.cpp L29](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/helper/adiosPluginManager.cpp#L29); [PluginEngineInterface.h L8-L60](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/plugin/PluginEngineInterface.h#L8-L60)]
10. **GPU buffers.** Variables can declare a memory space (Detect, Host, or GPU when built with GPU support), so data can be handed over straight from device memory. CUDA and Kokkos are optional dependencies. [KNOWN: [ADIOSTypes.h L39-L46](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/common/ADIOSTypes.h#L39-L46); [ReadMe.md L95-L124](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/ReadMe.md#L95-L124)]

## What stands out
Interpretation only.
- The design puts one decision, *where the bytes go*, behind a name lookup that can be changed at run time. Everything else (variables, selections, steps) stays the same. That's why one code can go from checkpoint files to live ML feeding without a rewrite. [INFERRED from IO.cpp and the docs]
- The project is shrinking its surface on purpose: legacy engines are off by default and marked for removal, and plugin engines moved to a public-API-only interface. That reads as a maintenance-cost decision. [INFERRED from README and PluginEngineInterface.h]
- The git log is far more multi-institutional than ORNL's copyright line suggests. Kitware and Georgia Tech addresses together account for about 46% of commits, ORNL addresses about 15%. [KNOWN: signals/adios2.md; INFERRED: the reading]

### Reusable ideas [INFERRED]
- **Factory table plus a "not compiled" placeholder.** Every optional backend gets an entry, and missing ones throw a precise message instead of failing silently ([IO.cpp L72-L158](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/IO.cpp#L72-L158)). This works for any app with optional plugins.
- **Rank-0 probe, then broadcast.** One process checks the filesystem and tells the others, so a missing file fails on every rank together instead of hanging the job ([IO.cpp L605-L607](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/core/IO.cpp#L605-L607)). The same applies to any distributed job that reads config.
- **Deferred-by-default writes with an explicit sync escape.** This lets the library batch and avoid copies. The price is a documented rule: don't reuse the buffer until the step ends.
- **A step as the atomic unit** for both files and streams. A reader loop that handles OK, NotReady and EndOfStream works for a finished file or a live feed.
- **Control plane / data plane split** behind a struct of function pointers ([dp_interface.h L327-L350](https://github.com/ornladios/ADIOS2/blob/e43363bd5596da4cf2d2c78d7c4940fb512fad2f/source/adios2/toolkit/sst/dp_interface.h#L327-L350)). Transports can be added without touching the protocol logic.
- **Tiered optional dependencies** documented for packagers (core, common, specialized, legacy), so distributions ship a lean build.
