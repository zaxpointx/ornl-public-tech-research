## Walkthrough (plain language)
- **What it is:** a GPU program that simulates how particles (electrons, positrons, photons, and lately muons and optical photons) travel through a particle-physics detector and deposit energy. It is meant to plug into Geant4, the standard CPU toolkit for this job, and take over the expensive particles. [KNOWN: [doc/index.rst L64-L72](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L64-L72), L172-L193]
- **The problem:** the High-Luminosity LHC upgrade will need more computing than CPU grids can supply. The docs cite a CMS forecast that requirements will exceed availability by more than a factor of two, with about 40% of that going to Monte Carlo detector simulation. [KNOWN: [doc/index.rst L56-L63](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L56-L63)]
- **What goes in:** a detector geometry (GDML, or a geometry already loaded in Geant4), physics settings, and particles. The particles are either primaries from a JSON input to the standalone `celer-sim` app, or tracks handed over one at a time by Geant4. [KNOWN: [README.md L153-L199](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/README.md#L153-L199); [TrackingManager.cc L129-L158](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/accel/TrackingManager.cc#L129-L158)]
- **What happens:** tracks fill a fixed-size array of "track slots" on the GPU. Each step iteration runs an ordered list of actions (initialize, pre-step, along-step, choose interaction, interact, cross boundaries, handle secondaries), and each action is one GPU kernel over all slots. [KNOWN: [doc/index.rst L197-L215](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L197-L215)]
- **What comes out:** energy deposits and hits in sensitive detectors (reported back to Geant4's sensitive-detector machinery when integrated), plus diagnostics and timing output. [KNOWN: `src/celeritas/ext/GeantSd.hh`, `detail/HitProcessor.hh` exist; INFERRED: the hand-back path, from those names and OSTI 2361202's mention of "detector hit scoring"]
- **Where humans act:** an experiment's software team adds a few lines to a Geant4 app: find the package in CMake, register the tracking-manager constructor on the physics list, and set options. The README shows the diff. [KNOWN: [README.md L78-L149](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/README.md#L78-L149)]
- **What it is not:** not a replacement for all of Geant4. Its "immediate goal" is EM physics, and Geant4 keeps hadronic physics. Not a reactor code either, though its ORANGE geometry is shared with ORNL's Shift (see Related projects). [KNOWN: doc/index.rst L68-L72; OSTI 3376506]
- **Example:** the README's `celer-sim` input fires 100 electrons at 10 MeV in random directions from the origin into a GDML geometry. [KNOWN: [README.md L159-L195](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/README.md#L159-L195)] The published result for the integrated case: on Summit, EM physics ran 6 to 32 times faster on the GPUs than CPU-only, and a Geant4 ATLAS test-beam app with full hadronic physics sped up 1.8 to 2.3 times overall. [KNOWN: OSTI 2361202 abstract (v0.3/0.4 era), https://www.osti.gov/biblio/2361202]
- **What's unknown:** which experiments run it in production today. The docs and papers report integration work and benchmarks, not production adoption.

## What it is (plain English, 2-4 sentences)
Celeritas is a Monte Carlo particle transport code for high-energy-physics detectors, written to run on NVIDIA and AMD GPUs. It works as a Geant4 accelerator: selected particles are "offloaded" to the GPU, simulated there, and their results returned. [KNOWN: doc/index.rst L64-L72] The docs call its Geant4 offload interface "the most stable and user-ready component". [KNOWN: [doc/index.rst L251-L256](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L251-L256)]

## How it works (plain English, no jargon without definition)
1. **Libraries in layers.** `corecel` (GPU/CPU abstractions), `geocel` (geometry interfaces and wrappers), `orange` (ORNL's portable geometry), `celeritas` (physics and track loop) and `accel` (Geant4 integration). There are also `larceler` (LArSoft) and `ddceler` (DD4hep) adapters. [KNOWN: [doc/index.rst L263-L269](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L263-L269); `src/` tree]
2. **Data model: Params / State / View.** *Params* are shared, read-only data (materials, cross sections, geometry), built on the host and copied to the GPU. *State* is per-track data in fixed slots. A *View* combines both for one slot, so the same physics code runs on host or device. [KNOWN: [data-model.rst L9-L40](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/implementation/data-model.rst#L9-L40)] The docs give the reason: storage must be "isolated from data use" for device code. [KNOWN: same lines]
3. **Loop interchange.** CPU codes loop over tracks and, inside that, over steps. Celeritas flips this. The outer loop is step iterations, the inner loop is track slots, and each step is a sorted list of actions, usually one kernel each. [KNOWN: [doc/index.rst L200-L212](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L200-L212)]
4. **Step actions in a fixed order.** The orders are generate, start, user_start, sort_start, pre, user_pre, sort_pre, along, sort_along, pre_post, sort_pre_post, post, user_post and end. [KNOWN: [ActionInterface.hh L28-L44](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/corecel/sys/ActionInterface.hh#L28-L44)] Each action implements `order()` plus `step()` for host and for device memory. [KNOWN: [ActionInterface.hh L175-L185](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/corecel/sys/ActionInterface.hh#L175-L185)] Actions are sorted by (order, id) and run in sequence, with optional per-action timing. [KNOWN: [ActionGroups.t.hh L52-L57](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/corecel/sys/ActionGroups.t.hh#L52-L57); [ActionSequence.cc L79-L143](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/celeritas/global/ActionSequence.cc#L79-L143)]
5. **Physics models are actions too.** For example, the Klein-Nishina Compton model's `.cu` file builds a track executor that only touches slots whose chosen post-step action is that model, then launches it as a kernel. [KNOWN: [KleinNishinaModel.cu L22-L32](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/celeritas/em/model/KleinNishinaModel.cu#L22-L32); [TrackExecutor.hh L177-L189](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/celeritas/global/TrackExecutor.hh#L177-L189)] `src/celeritas/em/model/` has about 20 such models (Bethe-Bloch, Bethe-Heitler, Livermore photoelectric, Møller-Bhabha, Seltzer-Berger, Rayleigh, Coulomb scattering, muon models, gamma- and electro-nuclear). [KNOWN: directory listing]
6. **One step, asynchronously.** `Stepper::async()` reserves room for new tracks, resets counters, runs the action sequence, then queues an asynchronous copy of the counters back to the host, which marks the step as complete. [KNOWN: [Stepper.cc L167-L199](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/celeritas/global/Stepper.cc#L167-L199)]
7. **CPU fallback.** On the host, the same executor runs in a plain loop, OpenMP-parallel over tracks when enabled, with exceptions collected per thread. [KNOWN: [ActionLauncher.hh L32-L55](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/celeritas/global/ActionLauncher.hh#L32-L55)]
8. **CUDA/HIP portability.** `CELER_FUNCTION` expands to `__host__ __device__` under either compiler. `DeviceRuntimeApi.hh` adds a `cuda` or `hip` prefix to runtime calls. The CMake build marks the shared `.cu` files as `LANGUAGE HIP` when HIP is on, so one source file serves both vendors. [KNOWN: [Macros.hh L36-L40](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/corecel/Macros.hh#L36-L40); [DeviceRuntimeApi.hh L15-L55](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/corecel/DeviceRuntimeApi.hh#L15-L55); [CeleritasLibraryUtils.cmake L95-L104](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/cmake/CeleritasLibraryUtils.cmake#L95-L104)]
9. **Geometry is chosen at build time.** `CELERITAS_CORE_GEO` is VecGeom, ORANGE or Geant4. CMake refuses VecGeom with HIP and refuses Geant4 geometry with any GPU or OpenMP build. [KNOWN: [CMakeLists.txt L206-L225](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/CMakeLists.txt#L206-L225); [CoreGeoParams.hh L11-L17](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/celeritas/geo/CoreGeoParams.hh#L11-L17)] So on AMD GPUs such as Frontier's, ORANGE is the only option. [INFERRED from those CMake rules] The docs describe ORANGE as surface-based and "platform portable", meaning it runs on GPUs from more than one vendor. [KNOWN: [doc/index.rst L151-L163](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L151-L163); [orange/README.rst L9-L16](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/orange/README.rst#L9-L16)]
10. **Geant4 offload.** `TrackingManager::HandOverOneTrack` pushes each eligible Geant4 track into a per-thread `LocalTransporter`, then kills the Geant4 copy. `LocalTransporter` double-buffers primaries, so Geant4 keeps filling one buffer while the GPU copies and steps the other, and it flushes at the end of each event. [KNOWN: [TrackingManager.cc L129-L158](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/accel/TrackingManager.cc#L129-L158); [LocalTransporter.hh L42-L79](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/accel/LocalTransporter.hh#L42-L79)] Other entry points are `UserActionIntegration` and `FastSimulationIntegration`. [KNOWN: README L141-L149]

## What stands out
Interpretation only.
- ORANGE is the hinge between ORNL's reactor-physics world (SCALE, Shift) and HEP. The same geometry engine tracks neutrons in Shift on Frontier and electrons in Celeritas. That is a rare public view of code moving across ORNL program lines. [INFERRED from OSTI 3376506, 2538455 and orange/README.rst]
- Public CI builds the GPU code but doesn't run it on GPUs. Real device testing happens by hand on Perlmutter and Frontier at release time. The public CI signal therefore understates GPU testing, and per-commit GPU regressions could slip through between releases. [INFERRED from build-docker.yml and administration.rst]

### Reusable ideas [INFERRED]
- **Loop interchange for divergent workloads.** Turn "for each item, run its steps" into "for each step type, run every item that needs it". Branchy per-item logic becomes a sequence of uniform kernels ([doc/index.rst L200-L212](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/doc/index.rst#L200-L212)). This pays off on GPUs and in vectorized CPU code.
- **Ordered action registry.** Each stage declares an `order()`, the framework sorts by (order, id), and user hooks slot in at named points (`user_pre`, `user_post`) ([ActionInterface.hh L28-L44](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/corecel/sys/ActionInterface.hh#L28-L44)). The same pattern fits any pipeline that wants plugins without a hand-written call order.
- **Params / State / View separation.** Immutable shared data, per-slot mutable state, and a cheap view object that joins them for one slot. Device-safe code follows from that structure, not from discipline alone.
- **Conditional executors.** A model's kernel runs over all slots but acts only where `post_step_action == my_id` ([TrackExecutor.hh L177-L189](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/celeritas/global/TrackExecutor.hh#L177-L189)). That gives a simple dispatch with no virtual calls on the device.
- **One source file for two GPU vendors.** A small macro layer (`CELER_FUNCTION`, `CELER_DEVICE_API_SYMBOL`) plus a CMake language override, instead of a heavy portability framework.
- **Fail at configure time** for incompatible options (VecGeom with HIP, for example) rather than at run time ([CMakeLists.txt L206-L225](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/CMakeLists.txt#L206-L225)).
- **Double-buffered producer/consumer offload.** The host keeps producing work while the device consumes the previous batch ([LocalTransporter.hh L51-L79](https://github.com/celeritas-project/celeritas/blob/e06590a2fa251851ffd3ce522bd374bac06c9b27/src/accel/LocalTransporter.hh#L51-L79)).
