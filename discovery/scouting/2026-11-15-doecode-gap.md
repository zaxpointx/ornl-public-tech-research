# Scouting: DOE CODE site-ownership gap and non-GitHub repositories (cyber first), 2026-11-15

Scope. Round 2, Scout C. Question: which public ORNL cybersecurity tools (then software-engineering and Linux/infrastructure security) exist as DOE CODE records that aren't on GitHub, or that `discovery/snapshots/doecode-2026-11-11.json` missed? Surfaces used on 2026-11-15: the documented DOE CODE search API (`GET https://www.osti.gov/doecodeapi/services/search?site_ownership_code=ORNL&rows=100&start=0..500`, six pages, docs at https://www.osti.gov/doecodeapi/markdown/Search.md), then single-record GETs (`/doecodeapi/services/search/{code_id}`) for 16 records. I also used the OSTI records API (`/api/v1/records`) to find papers named in or matching those records, the GitHub REST API for two code locations named by records or their landing pages, and WebFetch on five pages. Each of those pages is the exact `repository_link` or `landing_page` of a DOE CODE record, or a link shown on one. About 47 requests in all, a little over the 40 bound, because the diff took six pages plus 16 record GETs. The diff ran over raw JSON in the session scratchpad, outside the repo. No record carried `official_use_only` or `is_limited` (0 of 563), so none were skipped on that ground. No code.ornl.gov listing, explore page or guessed path was opened. The only code.ornl.gov pages reached are the exact `repository_link` URLs of DOE CODE 70505 and 172998: an HTTP status check on both, and one WebFetch on 70505. Neither showed a login page. Every candidate was checked by name, code_id and URL against `discovery/catalog.csv`, `discovery/leads.csv` (39 leads) and both snapshots. Round-1 candidates and the round-1 empty searches in `verification/not-found.md` weren't repeated.

Dedupe convention used here, an assumption for the coordinator to confirm. All 452 overlap records and most non-GitHub ORNL records are already in the DOE CODE snapshot, but only as raw collector metadata: none of the cyber ones below appear in the catalog, the lanes file or the leads. I record a snapshot-present record as a candidate only when it has no GitHub repository and isn't in the catalog or leads. Its notes say "snapshot-present". Snapshot-present records that are on GitHub are out of this question. They are listed separately under "Flag for the coordinator" and not counted.

## Top 3 for deeper study

1. **can-signal-clustering-masquerade (DOE CODE 134139 plus OSTI 1866690).** It aims straight at the gap the can-time-ids deep dive measured: timing detectors had recall 0 on ROAD's masquerades. The mechanism is to compare cluster structure across signals instead of frame timing, and to score a capture against benign and attack similarity distributions. The code is closed, but the paper is public, CluSim is open, and ROAD already has the signal-translated captures in `.cache/data/`. So a bounded reconstruction can test whether correlation structure catches the coolant and 0xD0 masquerades. A builder learns how to turn "relationships between signals broke" into a calibrated score.
2. **stucco.** It's the only candidate here with a full public codebase behind a cyber mechanism: 29 MIT repos, including entity and relation extractors, an auto-labeled cyber text corpus (97 stars), graph alignment and ansible deployment. It's dormant since about 2019, so it suits artifact study and code reading more than running. A builder learns an early end-to-end design for a security knowledge graph (collection, NLP extraction, conflict-resolving graph merge), which sits next to modern LLM-based CTI pipelines.
3. **d2u-user-emulator (DOE CODE 96071 plus OSTI 1813180).** It covers the realism side of cyber ranges: generative models of real users' application sequences that drive real applications, so the traffic isn't replayed. The code is closed, and the paper is the depth. It pairs with ai-atac-cyber-range, cyberwheel and the SOAR data. A builder learns why sequence-level behavior models matter to how believable IDS test data is. The idea could be rebuilt in a small agent-driven lab.

The runner-up is `cert-validation-libs`: tiny, public and runnable, but with little mechanism beyond correct x509 checks. The bigger lever is the coordinator flag: at least 15 snapshot-present GitHub records in the lanes (Systemd_Snapshot, certified, greggd, eBPF_communityID, pkpass, oidc-utils and others) have never been triaged. They are probably better deep candidates than anything in the closed-source set [INFERRED].
